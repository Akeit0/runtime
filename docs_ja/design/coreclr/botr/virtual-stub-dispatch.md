# 仮想スタブディスパッチ（Virtual Stub Dispatch）

著者: Simon Hall（[@snwbrdwndsrf](https://github.com/snwbrdwndsrf)）— 2006

## はじめに（Introduction）

Virtual Stub Dispatch（VSD）は、従来の仮想メソッドテーブル（vtable）の代わりに、仮想メソッド呼び出しをスタブ経由で行う手法です。過去の実装では、インターフェイスのディスパッチにはプロセス一意のインターフェイス識別子が必要で、ロードされたすべてのインターフェイスをグローバルな「インターフェイス vtable マップ」に追加していました。NGEN シナリオではこれにより、インターフェイスとそれを実装するすべてのクラスを実行時に復元する必要が生じ、起動時のワーキングセットが大きく増加していました。スタブディスパッチの動機は、このワーキングセットの多くを排除し、残りの作業をプロセスのライフタイム全体に分散させることです。

VSD は仮想インスタンス メソッドとインターフェイス メソッドの双方に適用可能ですが、現状ではインターフェイス ディスパッチにのみ使用されています。

## 依存関係（Dependencies）

### コンポーネントの依存（Component Dependencies）

スタブディスパッチのコードはランタイム本体とは比較的独立に存在し、利用側コンポーネントのための API を提供します。依存の表面積は小さく、以下に要点を挙げます。

#### コードマネージャ（Code Manager）

VSD は、メソッドが最終状態へ到達したか（スタブ生成やターゲット キャッシュの判断に必要）といった状態情報を得るため、コードマネージャに実質的に依存します。

#### 型とメソッド（Types and Methods）

`MethodTable` は、任意の VSD 呼び出しサイトに対するターゲットコードアドレスを決定するためのディスパッチ マップへのポインタを保持します。

#### 特殊な型（Special Types）

COM 相互運用の型に対する呼び出しは、それぞれ特殊なターゲット解決を持つため、カスタムディスパッチが必要です。

### このコンポーネントに依存するもの（Components Dependent on this Component）

#### コードマネージャ（Code Manager）

JIT コンパイラへインターフェイス呼び出しのターゲットを提供するため、コードマネージャは VSD に依存します。

#### クラスビルダー（Class Builder）

型の構築中にディスパッチ マップを作るため、クラスビルダーはディスパッチ マッピング コードが公開する API を使用します。これらのマップは後段の VSD によるディスパッチで利用されます。

## 設計目標（Design Goals and Non-goals）

### 目標（Goals）

#### ワーキングセット削減（Working Set Reduction）

従来のインターフェイス ディスパッチは、プロセス全体で共有されるインターフェイス ID を扱う大きく疎な vtable ルックアップ マップで実装されていました。必要に応じてディスパッチ スタブを生成することでコールドなワーキングセットを削減し、理論的には呼び出しサイトと対応するスタブを近接配置してワーキングセット密度を向上させることを狙います。

なお、VSD では各呼び出しサイトあたりの初期ワーキングセットは増えます。これは生成・収集される各種スタブを追跡するためのデータ構造が必要になるためです。ただし、アプリが定常状態に達すれば、単純なディスパッチにはこれらが不要になりページアウトされます。クライアント アプリでは起動時間の悪化につながり、仮想メソッドへの VSD を無効化した要因の一つとなりました。

#### スループットの同等性（Throughput Parity）

インターフェイス／仮想メソッドのディスパッチ性能が、従来の vtable メカニズムと償却的に同等であることが重要です。インターフェイス ディスパッチでは達成容易でしたが、仮想メソッド ディスパッチではやや低速になり、無効化の判断材料になりました。

## トークン表現とディスパッチ マップの設計（Design of Token Representation and Dispatch Map）

ディスパッチ トークンは、実行時に割り当てられる「インターフェイスとスロットの組（タプル）」を内包する、プラットフォームのワードサイズの値です。

設計では、割り当てられた型 ID 値とスロット番号の組み合わせを用います。ランタイムと統合しやすくするため、スロット番号の割り当ては従来の vtable レイアウトに揃えます。これにより、`MethodTable`／`MethodDesc`／スロット番号の扱いは従来どおりで、直接 vtable に触れる代わりにヘルパー経由でアクセスするだけの違いになります。

ここでいう「スロット」は、従来の vtable レイアウトにおけるスロット「インデックス」の意味で一貫して用います（先頭に仮想メソッド、その後に非仮想メソッドが並ぶ従来の `MethodTable` 表現を想像すると、そこでの位置）。ランタイム内部では「スロット」が「vtable 構造のインデックス」と「vtable エントリのアドレス」の両義で使われてきましたが、変更点は「スロットはインデックス値のみ」を指し、コードポインタの実体は「実装テーブル（後述）」に格納される、という点です。

動的に割り当てられる型 ID 値については後述します。

### メソッドテーブル（Method Table）

#### 実装テーブル（Implementation Table）

型が導入した各メソッド本体について、そのエントリポイントへのポインタを並べた配列です。並び順は次のとおりです。

- 新規導入（newslot）の仮想メソッド
- 新規導入の非仮想メソッド（インスタンス／static）
- 仮想メソッドのオーバーライド

この形式は従来 vtable の自然な拡張となるため、後述のスロット マップの多くのエントリは、クラスが持つ仮想／非仮想メソッド数などの情報とこの順序から推論できます。

現在、仮想インスタンス メソッドに対するスタブディスパッチは無効化されています。その場合、実装テーブルは存在せず、真の vtable に置き換えられます。マッピング結果は実装テーブルのインデックスではなく、vtable のスロットとして表現されます。本ドキュメントで実装テーブルに言及する際はこの点に留意してください。

#### スロット マップ（Slot Map）

スロット マップは、0 個以上の `<type, [<slot, scope, (index | slot)>]>` エントリからなるテーブルです。`type` は前述の動的な型 ID で、現在のクラス（仮想インスタンス メソッド呼び出し）を示すセンチネル、または現在のクラス（もしくはその親のいずれか）が実装するインターフェイスを表します。角括弧内のサブマップには 1 個以上のエントリがあり、各エントリの第 1 要素は常に `type` 内のスロットを指します。第 2 要素 `scope` は第 3 要素が「実装テーブルの `index`」か「`slot` 番号」かを指定します。`scope` が既知のセンチネル値である場合、次の値は仮想スロット番号として解釈され、`this.slot` として仮想解決されます。`scope` が継承階層内の特定クラスを識別する場合、第 3 要素はそのクラスの実装テーブルへの `index` で、`type.slot` の最終的なメソッド実装を指します。

### 追加用途（Additional Uses）

このマッピング手法は、`methodimpl` による仮想スロットの再マッピング（＝現在のクラスのマップ内で、インターフェイス スロットを仮想スロットに対応付けるのと同様の指定）にも利用できます。スコープ指定により非仮想メソッドも参照できるため、将来的に「非仮想メソッドでインターフェイスを実装する」といった方向にも拡張可能性があります。

### 最適化（Optimizations）

スロット マップはビットエンコードされ、典型的なインターフェイス実装パターンをデルタ値で表現することでサイズを大幅に削減しています。さらに、新規スロット（仮想／非仮想）は実装テーブル内の順序から暗黙に決定できます。すなわち「新規仮想 → 新規インスタンス → オーバーライド」の順で並ぶとき、親クラスから継承した仮想メソッド数と組み合わせて、実装テーブルのインデックスからスロット マップの多くを推論できます。こうした暗黙エントリは（\\*）で示されます。現在のデータ構造の配置は次のとおりで、実装テーブルの順序だけで完全に推論できない場合にのみ `DispatchMap` が存在します。

```
MethodTable -> [DispatchMap ->] ImplementationTable
```

## 型 ID マップ（Type ID Map）

未割当ての型に遭遇するたびに単調増加で ID を割り当て、型から ID への対応関係を管理します。現状、対象となる型はすべてインターフェイスです。実装は双方向検索可能な HashMap です。

## ディスパッチ トークン（Dispatch Tokens）

ディスパッチ トークンは `<typeID, slot>` のタプルです。インターフェイスの場合、`typeID` はそのインターフェイスに割り当てられた ID です。仮想メソッドの場合、`this` に対する仮想解決を意味する定数値を `typeID` に用います。多くの場合、このペアはプラットフォームのネイティブ ワードに収まります。x86 ではそれぞれの下位 16bit を結合する形になるでしょう。`TypeHandle` と同様のセンチネルでの拡張（オーバーフロー処理のため `<TypeHandle,TypeHandle>` のようなペア表現を使い分ける）も一般化は可能ですが、必要性は未確定です。

## 仮想スタブディスパッチの設計（Design of Virtual Stub Dispatch）

### ディスパッチ トークンから実装への解決（Dispatch Token to Implementation Resolution）

トークンと型が与えられれば、その型に対する実装テーブルのインデックスへマップして実装を求めます。実装テーブルは型の `MethodTable` から到達できます。マップは `BuildMethodTable` で作成されます。ここでは対象型が実装するすべてのインターフェイスを列挙し、対象型が実装/オーバーライドするすべてのインターフェイス メソッドを決定します。これを保持しておくことで、インターフェイス ディスパッチ時に、トークンとターゲット オブジェクト（から得られる `MethodTable` とトークン マッピング）に基づいてターゲット コードを決定できます。

### スタブ（Stubs）

インターフェイス ディスパッチはスタブ経由で行われます。スタブはすべてオンデマンド生成され、最終的には「トークンとオブジェクトを実装に対応付け、その実装にフォワードする」役目を担います。スタブは 3 種類があり、以下の図の制御フローで連携します。

![Figure 2](images/virtualstubdispatch-fig2.png)

#### ジェネリック リゾルバ（Generic Resolver）

実体は C 関数で、すべてのスタブの最終フォールバックです。`<token, type>` を受け取り、ターゲットを返します。ディスパッチ／リゾルバ スタブの生成、間接セルのパッチ適用、結果のキャッシュ、各種ブックキーピングも担います。

#### ルックアップ スタブ（Lookup Stubs）

これはインターフェイス呼び出しサイトに最初に割り当てられるスタブで、JIT がインターフェイス呼び出しサイトをコンパイルする際に作成されます。初回呼び出しまで、JIT はトークンを満たす型を知りません。そのため、このスタブはトークンと型をジェネリック リゾルバへ渡します。必要に応じて、リゾルバはディスパッチ／リゾルブ スタブを生成し、呼び出しサイトをディスパッチ スタブへバックパッチします（以後ルックアップ スタブは使われません）。同一のインターフェイス スロットに対する呼び出しサイトは同一のルックアップ スタブを共有します。

#### ディスパッチ スタブ（Dispatch Stubs）

呼び出しサイトが単相（モノモーフィック）とみなせる場合に使われます。すなわち、そのサイトで用いられるオブジェクトの型が概ね一定であるケースです。ディスパッチ スタブは対象オブジェクトの `MethodTable` を取得し、キャッシュ済みの型と比較して一致すればキャッシュ済みターゲットへジャンプします（x86 では比較／失敗分岐／ターゲット ジャンプの短い列）。一致しなければ対応するリゾルブ スタブにジャンプします。`<token, type>` ごとに 1 個のディスパッチ スタブが生成されます（遅延生成。ルックアップ スタブが呼ばれたとき）。

#### リゾルブ スタブ（Resolve Stubs）

多相（ポリモーフィック）な呼び出しサイトを扱います。`<token, type>` をキーに、グローバル キャッシュからターゲットを解決します。見つからなければジェネリック リゾルバを呼び、その返したターゲットにジャンプします。リゾルバは `<token, type, target>` をキャッシュに挿入するため、同じキーでの次回呼び出しはキャッシュヒットします。

ディスパッチ スタブの失敗が一定回数を超えると、そのサイトは多相と判定され、失敗コストを避けるため呼び出しサイトはリゾルブ スタブへ直接バックパッチされます。GC 終了などの同期点で、ポリモーフィック判定されたサイトの一部はランダムに単相へ「再昇格」されます（多相性は通常一時的という仮定）。仮定が誤っていれば、すぐに再び多相へ降格されます。リゾルブ スタブはトークンごとに 1 個生成され、全スタブでグローバル キャッシュを共有します。トークンごとにスタブを分けることで、`<token, type>` の不変部分から事前計算したハッシュを用いた高速なルックアップが可能になります。

## 現状（Current State）

現在、VSD はインターフェイス メソッド呼び出しに対してのみ有効で、仮想インスタンス メソッド呼び出しには無効です。理由は主に次の通りです。

- 起動（Startup）: 初期スタブ生成の必要から、起動時のワーキングセットと速度に負荷がかかった。
- スループット（Throughput）: インターフェイス ディスパッチは一般に高速化する一方で、仮想インスタンス メソッドは許容しがたい低下が見られた。

その結果、すべての型は仮想インスタンス メソッド用に vtable を持ち、上述の実装テーブルは無効化されています。インターフェイス メソッドのディスパッチを可能にするため、ディスパッチ マップは依然として存在します。
