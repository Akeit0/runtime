# 共通言語ランタイム（CLR）入門（Introduction to the Common Language Runtime (CLR)）

Vance Morrison（[@vancem](https://github.com/vancem)）著 — 2007

Common Language Runtime（CLR）とは何か？ 端的にいえば、

> Common Language Runtime（CLR）は、多様なプログラミング言語とその相互運用を支えるために設計された、完全で高水準な仮想マシンである。

この一文だけでは直感的にわかりにくいかもしれません。しかし、巨大かつ複雑なソフトウェアである [CLR][clr] の機能を、理解しやすいまとまりとして捉える最初の一歩としては有用です。まず「鳥瞰図（1 万フィートビュー）」を得ることで、ランタイムの大きな目的と狙いを把握し、そのうえで細部（サブコンポーネント）に迷わず進めるようになります。

## CLR: （非常に稀な）完全なプログラミング基盤

あらゆるプログラムは、実行時環境に多くの依存を持ちます。最も明らかなのは言語そのものですが、それは前提の一つにすぎません。現実的なプログラムは、入出力・ファイル・ネットワークなどマシン資源とやり取りするための「ランタイム ライブラリ」を必要とし、さらにネイティブ ハードウェアが直接実行できる形へ（インタプリタやコンパイルにより）変換される必要があります。これらの依存は数も種類も多く、互いに絡み合うため、言語実装者は多くを別の標準に委ねがちです。たとえば C++ は実行ファイル形式を規定しません。各 C++ コンパイラは特定のハードウェア（例: x86）と OS（例: Windows, Linux, macOS）に結びついており、その環境が実行形式の仕様やロード方法を定めます。結果として、私たちは「C++ 実行ファイル」ではなく「Windows x86 実行ファイル」等を作ることになります。

既存のハードウェアや OS 標準を活用するのは有益ですが、その抽象度に縛られる不利があります。例えば一般的な OS はガベージコレクション（GC）ヒープの概念を持ちません。よって、GC を前提にした高水準なやり取り（例: 文字列の受け渡しで解放責務を気にしない）を既存標準だけで表現できません。同様に、典型的な実行形式は「実行に必要な最小限の情報」しか持たず、コンパイラが他バイナリへ適切にバインドするための情報は不足します。たとえば C++ では msvcrt.dll のような標準ライブラリがあっても、対応するヘッダ（stdio.h 等）がなければ利用できません。つまり「実行可能形式の規定」と「完全なプログラムとして必要な周辺情報」の両方を既存の実行形式規格だけで満たすことは困難です。

CLR はこうした問題に対し、プログラムのライフサイクル（生成・バインディング・展開・実行）全体に必要な詳細を含む[非常に完全な仕様][ecma-spec]（ECMA 標準）を定義することで解決します。具体的には次を規定します。

- GC を前提とした独自命令セット（Common Intermediate Language; CIL）を持つ仮想マシン。CPU 依存を排します。
- 型・フィールド・メソッド等の宣言を表す豊富なメタデータ。外部の機能呼び出しに必要な情報をコンパイラへ提供します。
- OS やハードウェアに依存しない CLR EXE を厳密に表現できるファイル形式。
- ロード後のライフタイム セマンティクス、他の CLR EXE 参照の仕組み、実行時に参照を解決する規則。
- CLR の機能（GC、例外、ジェネリクス等）を活用したクラス ライブラリ（基本機能と OS サービス双方）。

### 多言語対応（Multi-language Support）

これらの詳細の定義・仕様化・実装は大事業であり、完全な抽象化（CLR のようなもの）が稀な理由でもあります。多くは単一言語向けに作られてきました（Java ランタイム、Perl インタプリタ、初期 Visual Basic ランタイム等）。CLR を特に特徴づけるのは、その「多言語性」です。言語内部だけを見れば良好でも、他言語との相互運用は困難になりがちです。従来は OS が提供する低水準プリミティブ（GC ヒープの概念すらない）のみで言語間連携を行う必要があり、手法が複雑化していました。CLR は「共通言語ランタイム」を提供することで、GC 収集対象の構造体など高水準の構成要素で言語間がやり取りでき、相互運用の負担を大きく軽減します。

またランタイムを複数言語で共有することにより、デバッガやプロファイラなどの基盤を共用でき、各言語の負担を下げられます。さらに CLR 上に構築されたクラス ライブラリの全てへ即座にアクセスできることも大きな利点です。こうした豊富で成熟した機能群が CLR 成功の大きな要因になりました。

要するに、CLR は「プログラムを作成し実行するために必要なビット列」を完全に規定し、それを高水準仮想マシン上で実行します。この仮想マシンと、その上で動く膨大なクラス ライブラリ群の総体が、共通言語ランタイム（CLR）です。

## CLR の第一目標（The Primary Goal of the CLR）

CLR が何者かを掴んだところで、その解決しようとした問題を振り返ります。非常に高いレベルでは、CLR の目標はただ一つです。

> CLR の目標は、プログラミングを容易にすること。

この指針は CLR の進化において非常に有用です。根本的に、簡単なものだけが本当に「易しい」ため、ユーザーに露出する複雑さは極力避けるべきです。コスト/便益だけでなく、「露出する複雑さの増加 / すべてのシナリオに対する加重便益」の比を小さく保つことが重要です（理想は負、すなわち制約除去や一般化で複雑さを下げること）。

そして何より、「使いやすさ」こそが CLR 成功の根本理由です。ネイティブより常に高速・小容量だからでも、単一の特長機能（GC、プラットフォーム非依存、OOP、バージョニング等）のおかげでもありません。これら多くの機能が組み合わさることで、プログラミングを大幅に簡単にしているからです。しばしば見落とされがちな要素としては次があります。

1. 簡素化された言語（例: C# や VB は C++ より単純）
2. クラス ライブラリの単純さへの献身（例: 文字列型は 1 種で不変。文字列を使うあらゆる API が簡単になる）
3. 一貫した命名規約（省略語を避け、全体で統一）
4. 強力なツール連携（例: Visual Studio と IntelliSense による開発体験）

この「使いやすさ」への徹底（＝ユーザーモデルの単純さ）は、CLR の成功を支える決定要因です。

## 基本機能の柱

この後の節では、CLR を支える基本機能を概観します。

### ガベージコレクション（Garbage Collection）

CLR は自動メモリ管理（GC）を提供します。メモリ解放の責務から開発者を解放し、解放忘れや二重解放、解放後利用（Use-after-free）等のクラスのバグを根本から排除します。GC はヒープ上の生存オブジェクトを追跡し、不要になったオブジェクトを回収、断片化を抑えるための圧縮も行います。これにより、より単純なプログラミングモデルと高い信頼性を両立します。

### メモリ／型安全性（Memory and Type Safety）

CLR は実行時に型システムと検証により、バッファオーバーラン等の未定義動作を抑止します。厳密な型安全性と検証により、実行時の多くのエラーをクラス境界で遮断し、安全性と隔離性を高めます。

### 高水準言語機能の支援（High-Level Language Features）

CLR は例外処理、ジェネリクス、反射（リフレクション）などの高水準機能を一次機能として支えます。これにより、複数言語が同一の高水準抽象を共有でき、ライブラリ設計も統一されます。

## アーキテクチャ外の補助的機能

以下は GC や型安全性といった根幹以外の、完全なランタイムとして重要な機能です。

### アンマネージ コードとの相互運用（Interoperation with Unmanaged Code）

マネージ コードはアンマネージ コードの機能を利用できる必要があります。主に 2 形態があります。第一は単純にアンマネージ関数を呼ぶ形（P/Invoke）。第二は COM（Component Object Model）を介した、より構造化された相互運用です。CLR は COM とモデル（オブジェクト表現、エラー処理、ライフタイム等）を橋渡しするための特別な支援を持ち、より良い相互運用を実現します。

### 事前コンパイル（Ahead of time Compilation）

CLR では配布単位は CIL であり、ネイティブ化は実行時に行われます。最適化として、JIT 生成したネイティブ コードをファイルに保存する仕組み（`crossgen`、.NET Framework の NGEN に類似）を利用できます。巨大なクラス ライブラリで実行時コンパイル時間を削減するのに有効です。

### スレッディング（Threading）

CLR は当初からマルチスレッドを想定し、`System.Threading.Thread` により OS スレッドを 1:1 でラップします。ただしスレッド生成は比較的高コストです。短い作業単位を大量に処理するスタイル（Web サーバーの 1 リクエストなど、マルチコア並列アルゴリズムなど）では、キューイング可能なワーク アイテムを ThreadPool へ投げるモデルが有効です。推奨は [Task Parallel Library](https://msdn.microsoft.com/en-us/library/dd460717(v=vs.110).aspx) を用いる方法です。

実装面では、ThreadPool がスループットを最大化するようスレッド数を動的に制御します。これにより開発者は「並列性の露出」（ワーク アイテムの生成）に集中でき、適切な並列度の調整（ワークロードやハードウェア依存）を ThreadPool に委ねられます。

## まとめとリソース（Summary and Resources）

ランタイムは非常に多くを担います。本稿は内部詳細に踏み込まずとも、その理解のための有用な枠組みを提供することを目指しました。要点は次の通りです。

- ランタイムはプログラミング言語を支える完全な基盤である。
- 目標は「プログラミングを容易にする」こと。
- 基本機能の柱は以下。
  - ガベージコレクション
  - メモリ／型安全性
  - 高水準言語機能の支援
