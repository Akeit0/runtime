# CLR のスレッディング概要（CLR Threading Overview）

## マネージ スレッドとネイティブ スレッド（Managed vs. Native Threads）

マネージ コードは OS が提供するネイティブ スレッドとは異なる「マネージ スレッド」で実行されます。ネイティブ スレッドは物理マシン上でのネイティブ コードの実行単位、マネージ スレッドは CLR の仮想マシン上での仮想的な実行単位です。

JIT コンパイラが「仮想的な」IL 命令を物理マシンで動くネイティブ命令にマップするのと同様に、CLR のスレッド基盤は「仮想的な」マネージ スレッドを OS のネイティブ スレッドにマップします。

任意の時点で、マネージ スレッドはネイティブ スレッドに割り当てられている場合と、いない場合があります。例えば `new System.Threading.Thread` で作成され `Start` されていなければ、まだネイティブ スレッドに未割当のマネージ スレッドです。理論上、実行中に複数のネイティブ スレッド間を移動することもあり得ますが、実際には CLR は現在それをサポートしていません。

公開されている `Thread` API は、基盤となるネイティブ スレッドの詳細を意図的に隠蔽します。理由は次の通りです。

- マネージ スレッドは単一のネイティブ スレッドに必ずしも対応しない（そもそも対応しない場合もある）。
- OS によりネイティブ スレッドの抽象が異なる。
- 原則としてマネージ スレッドは「仮想化」されている。

CLR は独自にマネージ スレッドの等価な抽象を提供します。例えば OS の TLS は露出せず、代わりにマネージの「スレッド スタティック」変数が提供されます。ネイティブの「スレッド ID」も露出せず、OS と独立に生成される「マネージ スレッド ID」を提供します。診断目的では `System.Diagnostics` 名前空間の型を通じてネイティブ側の一部詳細を得られます。

マネージ スレッドはネイティブに不要な追加機能を必要とします。第一に、スタック上に GC 参照を保持するため、GC のたびに CLR がそれらを列挙（必要に応じて更新）できなければなりません。そのためには、各マネージ スレッドを GC 参照が全て見つかる地点で「サスペンド」する必要があります。第二に、AppDomain をアンロードする際、その AppDomain 内でコードを実行しているスレッドがないことを保証せねばなりません。CLR は該当スレッドに `ThreadAbortException` を注入して巻き戻します。

## データ構造（Data Structures）

すべてのマネージ スレッドには、[threads.h][threads.h] で定義される `Thread` オブジェクトが対応します。ここには VM がスレッドについて知るべき情報（現在の GC モード、`Frame` チェーンなどの必須情報に加え、性能目的のスレッド単位アロケータ等）が格納されます。

すべての `Thread` は `ThreadStore`（同じく [threads.h][threads.h]）に保持され、既知の `Thread` のリストになっています。全マネージ スレッドを列挙するには `ThreadStoreLock` を取得し、`ThreadStore::GetAllThreadList` を使います。未開始のスレッドや、対応するネイティブ スレッドが既に終了したものも含まれることがあります。

[threads.h]: https://github.com/dotnet/runtime/blob/main/src/coreclr/vm/threads.h

ネイティブ スレッドに割り当て済みの各マネージ スレッドは、そのネイティブ スレッド上の TLS スロットから到達できます。これにより実行中のネイティブ スレッドから `GetThread()` で対応する `Thread` を取得できます。

多くのマネージ スレッドは、ネイティブの `Thread` とは別に「マネージの `System.Threading.Thread` オブジェクト」も持ちます。これはマネージ コードからの操作用で、概ねネイティブ `Thread` の機能をラップします。現在のマネージ `Thread` は `Thread.CurrentThread` から取得できます。

デバッガでは SOS 拡張の `!Threads` で `ThreadStore` 内の全 `Thread` を列挙できます。

## スレッドのライフタイム（Thread Lifetimes）

マネージ スレッドは次の状況で生成されます。

1. マネージ コードが `System.Threading.Thread` で明示的に作成を要求したとき。
2. CLR が直接生成したとき（後述の[特殊スレッド](#special-threads)）。
3. ネイティブ スレッドが、まだマネージ スレッドに関連付いていない状態でマネージ コードを呼び出したとき（リバース P/Invoke や COM 相互運用）。
4. マネージ プロセスの開始時（メイン スレッドで `Main` が呼ばれる）。

ケース #1/#2 では、CLR がバックエンドのネイティブ スレッド生成を担います（スレッドが「開始」されるまで生成しません）。このネイティブ スレッドの寿命は CLR が管理します。ケース #3/#4 では、ネイティブ スレッドは既に存在し、CLR 外部が所有します。初めてマネージ コードを呼ぶ時に CLR が認識します。

ネイティブ スレッドが終了すると、CLR は `DllMain` を通じて通知を受けます（OS のローダー ロック内で発生）。この場では安全にできることが限られるため、対応するマネージ スレッドのデータ構造は即時破棄せず「dead」印のみ付け、ファイナライザ スレッドを起動します。ファイナライザが `ThreadStore` を掃引し、dead であり、かつマネージ コードから到達不能なスレッドを破棄します。

## サスペンド（Suspension）

GC を行うには、管理対象オブジェクトへの全参照を見つける必要があります。マネージ コードは常にヒープへアクセスし、スタックやレジスタ上の参照を操作しています。CLR は安全かつ確実に全オブジェクトを見つけるため、すべてのマネージ スレッドを停止しなければなりません。停止は、レジスタとスタック上のライブ参照が検査できる「安全点（safe point）」でのみ行います。

この「ロック」に相当する概念を、CLR ではスレッドの「GC モード」と呼びます。「協調（cooperative）モード」のスレッドはロックを握っており、GC を進めるにはロックを解放（プリエンプティブへ遷移）して協調する必要があります。「プリエンプティブ（preemptive）モード」のスレッドはロックを握っておらず、そのスレッドがヒープに触れていないことが保証されるため、GC はプリエンプティブに進行できます。

GC は、全マネージ スレッドがプリエンプティブ モードにあるときにのみ進行できます（これを「EE のサスペンド」とも呼びます）。

### 協調モードへ入る（Entering Cooperative Mode）

スレッドは `Thread::DisablePreemptiveGC` を呼ぶことで協調モードへ入ります（ロックの獲得）。手順は概ね次の 2 点を原子に行うのと同等です。

1. GC 進行中であれば（GC がロックを保持）、完了まで待機する。
2. 自スレッドを協調モードとマークする（この間 GC は進行不可）。

### プリエンプティブ モードへ入る（Entering Preemptive Mode）

`Thread::EnablePreemptiveGC` を呼ぶとプリエンプティブ モード（ロックの解放）へ移行します。協調モードのマークを外し、GC スレッドに進行可能性を通知します。

### EE のサスペンド（Suspending the EE）

GC が必要になれば、まず EE をサスペンドします。`GCHeap::SuspendEE` は概ね次のように進みます。

1. グローバル フラグ `g_fTrapReturningThreads` をセットし、GC 進行中であることを示す（協調モードへ入ろうとするスレッドは GC 完了までブロック）。
2. 協調モードで実行中の全スレッドを見つけ、それぞれを「ハイジャック」して協調モードから離脱させる。
3. 協調モードのスレッドが無くなるまで繰り返す。

### ハイジャック（Hijacking）

GC サスペンドのためのハイジャックは `Thread::SysSuspendForGC` により行われ、協調モードで実行中のマネージ スレッドを「安全点」で協調モードから離脱させます。手順の概要は次のとおりです。

1. 基盤のネイティブ スレッドを Win32 `SuspendThread` で停止する（任意の命令地点で強制停止されるため、安全点とは限らない）。
2. `GetThreadContext` でスレッドの `CONTEXT`（レジスタ状態）を取得し、現在の命令ポインタから実行中のコード種別を把握する。
3. スレッドが既にプリエンプティブに戻っていないか再確認。戻っていれば、任意のネイティブ コードを実行中かもしれないため直ちに再開する（デッドロック回避）。
4. マネージ コードを実行中か確認。協調モードのネイティブ VM コード実行中であれば、前項同様に直ちに再開する。
5. マネージ コード実行中で停止している場合:
   - 完全割り込み可能（fully interruptible）なコードなら、どの地点も安全点。だが歴史的な OS バグの回避のため、取得済み CONTEXT に頼らず、命令ポインタを書き換えてスタブへ遷移させる。このスタブは完全な CONTEXT を再取得し、協調→プリエンプティブへ切り替えて GC 完了を待ち、元の状態を復元する。
   - 部分割り込み可能（partially interruptible）なコードなら、現在地点は安全点でない。呼び出し元の戻り（メソッド遷移）は安全点なので、トップフレームのリターンアドレスをスタック上で上書きし、戻り先を前述のスタブへ差し替える（JIT が挿入した GC poll により先に協調離脱してハイジャックが解消される場合もある）。

## ThreadAbort / AppDomain アンロード（ThreadAbort / AppDomain-Unload）

AppDomain をアンロードするには、その AppDomain でコードを実行するスレッドが存在しないことを保証する必要があります。CLR は全マネージ スレッドを列挙し、スタック フレームが当該 AppDomain に属するスレッドを「アボート」します。`ThreadAbortException` をスレッドへ注入し、巻き戻し（バックアウト コードを実行しながら）を促進して AppDomain 外に出た時点で `AppDomainUnloaded` へ変換します。

`ThreadAbortException` は特別な例外で、ユーザー コードで捕捉可能ですが、ハンドラー実行後に CLR により必ず再スローされます（厳密な意味では「キャッチ不可」ではない）。通常はスレッドに「アボート中」ビットを立てるだけで十分ですが、長いループなどでチェックされない場合は、GC サスペンド時と同様のハイジャックで強制的に `ThreadAbortException` を発生させます。任意地点で発生し得るため、この仕組みは AppDomain アンロード以外の目的に使うべきではありません。

## 同期（Synchronization）

### マネージ（Managed）

`System.Threading` には多くの同期プリミティブがあります（Mutex/Event/Semaphore などの OS ラッパー、Barrier/SpinLock 等）。ただし多くの場面で主役となるのは `System.Threading.Monitor` で、任意のマネージ オブジェクトに対する高性能なロックと、条件変数的な待機/通知を提供します。

`Monitor` はスピンロックとカーネル ロック（Mutex 的）のハイブリッドです。多くのロックは短時間で解放されるため、少しの間だけスピンしたほうがカーネル遷移より速い場合が多い一方、CPU を浪費しないよう一定時間でブロッキングにフォールバックします。

任意オブジェクトがロック/条件変数として使われ得るため、各オブジェクトはロック情報の保存先を持つ必要があります。これは「オブジェクト ヘッダー」と「シンク ブロック」で実現します。オブジェクト ヘッダー（各オブジェクト先頭のワード）はハッシュコード等の用途に使われ、余地があればロック状態（保有スレッドのマネージ スレッド ID、未保有なら 0）も保持します。スピンで取得できない、またはヘッダーが他用途で埋まっている場合は、`Sync Block Table` にシンク ブロックを作成し、イベントで効率的に待機します。`Monitor.Wait/Pulse` による条件変数利用時は常にインフレート（シンク ブロック必須）です。詳細は [syncblk.h][syncblk.h]/[syncblk.cpp][syncblk.cpp] 参照。

[syncblk.h]: https://github.com/dotnet/runtime/blob/main/src/coreclr/vm/syncblk.h
[syncblk.cpp]: https://github.com/dotnet/runtime/blob/main//src/coreclr/vm/syncblk.cpp

### ネイティブ（Native）

VM のネイティブ コードも複数スレッドから呼ばれるため同期が必要です。`ITaskHost` によりホストはスレッド生成/破棄/同期の多くをオーバーライドできるため、VM は OS のプリミティブ（Critical Section/Mutex/Event 等）を直接ではなく、VM のラッパーを通じて利用します。

また GC サスペンドは VM のほぼ全域に影響する特別な「ロック」であり、ネイティブ コードでも GC ヒープに触れる場合は協調モードへ入る必要があります。このため GC モードと `Crst` が主要な同期手段となります。

#### GC モード（GC Mode）

マネージ コードは原則協調モードで動作しますが、通常のネイティブ コードはヒープに触れないためプリエンプティブです。ただし VM 内の一部ネイティブ コードはヒープに触れる必要があり、協調モードで動作します。ネイティブ側では直接モードを切り替えず、`GCX_COOP`/`GCX_PREEMP` マクロでスコープ付きに切り替え、スコープ終了で元に戻します。協調モードは GC ヒープに対する実質的なロックであり、ネイティブ コードはハイジャックできないため明示的に戻すまで維持されます。協調モード入りは極力短く保ち、ブロックやロック取得を避けるべきです。`GCX_PREEMP` は保持していたロックの解放に等しいため、参照の保護に細心の注意が必要です。関連する規律は [Rules of the Code](../../../coding-guidelines/clr-code-guide.md) を参照。

#### Crst

マネージの `Monitor` に相当する VM 向けの推奨ロックが `Crst` です。ホストや GC モードを理解するハイブリッド ロックで、[BotR の Crst レベリング](../../../coding-guidelines/clr-code-guide.md#2.6.4) に従ってデッドロック回避を行います。協調モード中の Crst 取得は原則禁止（やむを得ない場合の例外あり）。

## 特殊スレッド（Special Threads）

CLR はマネージ コードが生成するスレッドに加え、内部用途の「特殊スレッド」を作成します。

### ファイナライザ スレッド（Finalizer Thread）

マネージ コードを実行する全プロセスで生成されます。GC がファイナライズ対象オブジェクトの到達不能を検出するとキューへ入れ、GC 終了時にこのスレッドがキュー内のファイナライザを順次実行します。低メモリ通知など外部イベントの待機や内部のハウスキーピングにも用いられます（`GCHeap::FinalizerThreadStart` 参照）。

### GC スレッド（GC Threads）

「concurrent」や「server」モードでは、GC はバックグラウンド スレッドを 1 本以上生成し、ガベージコレクションの各段階を並列化します。これらは GC が完全に所有し、マネージ コードは実行しません。

### デバッガ スレッド（Debugger Thread）

各マネージ プロセスに 1 本のネイティブ スレッドを維持し、アタッチされたマネージ デバッガのための各種タスクを実行します。

### AppDomain-Unload スレッド（AppDomain-Unload Thread）

AppDomain のアンロードを担当します。要求元スレッドではなく CLR 内部の別スレッドで実行するのは、a) アンロード ロジック用のスタック領域を保証する、b) 必要に応じて要求元スレッドを当該 AppDomain から巻き戻せるようにする、ためです。

### ThreadPool スレッド（ThreadPool Threads）

`ThreadPool` はユーザーのワーク アイテムを実行するためのマネージ スレッド群を保持し、ThreadPool 所有のネイティブ スレッドにバインドします。また、スレッド注入・タイマー・登録待ちなどのための少数のネイティブ スレッドも維持します。

## 特殊スレッド（Special Threads）

デバッガ サポート、AppDomain アンロード、ThreadPool（ワーク アイテム、タイマー、登録待ち）に関わるスレッドなど、CLR が管理する各種スレッドについては、続く節に整理されています（追補予定）。
