# ガーベジコレクションの設計

著者: Maoni Stephens ([@maoni0](https://github.com/maoni0)) - 2015年

**注記:** ガーベジコレクション（GC）全般については *The Garbage Collection Handbook* を、CLR GC の具体的な知識については *Pro .NET Memory Management* を参照してください。両書籍は本ドキュメント末尾のリソース欄に記載しています。

---

## コンポーネントアーキテクチャ

GC に属するコンポーネントは 2 つあります。

1. **アロケータ (allocator)**
2. **コレクタ (collector)**

アロケータは追加メモリの取得と、適切なタイミングでコレクタを呼び出す役割を担います。
コレクタは不要になったオブジェクト（プログラムから参照されていないオブジェクト）のメモリを回収します。

コレクタが呼び出される方法は他にもあり、たとえば手動で `GC.Collect` を呼び出す場合や、ファイナライザスレッドが低メモリの非同期通知を受け取った場合（これがコレクタを起動する）などです。

---

## アロケータの設計

アロケータは実行エンジン (Execution Engine; EE) 内の割り当てヘルパーから以下の情報を受け取って呼び出されます。

* 要求サイズ
* スレッドの割り当てコンテキスト
* オブジェクトがファイナライザを持つかどうかなどを示すフラグ

GC はオブジェクト型ごとの特別な扱いは行いません。オブジェクトサイズは EE から取得します。

サイズに基づき、GC はオブジェクトを以下 2 種類に分類します。

* **小オブジェクト**（< 85,000 バイト）
* **大オブジェクト**（≥ 85,000 バイト）

原理的には両者を同じ方法で扱えますが、大オブジェクトのコンパクションは高コストのため区別しています。

---

### 割り当てコンテキストとアロケーション量子

GC がアロケータにメモリを渡すときは、**割り当てコンテキスト (allocation context)** 単位です。割り当てコンテキストのサイズは **アロケーション量子 (allocation quantum)** によって定義されます。

* **割り当てコンテキスト**: あるヒープセグメント内の小さめの領域で、特定スレッド専用に確保されます。単一プロセッサ（1 論理 CPU）環境では gen0 用の単一コンテキストが使われます。
* **アロケーション量子**: アロケータが追加メモリを確保するときの単位サイズ。通常 8KB で、平均オブジェクトサイズが約 35 バイトのため、多数のオブジェクト割り当てに使えます。

大オブジェクトは割り当てコンテキストや量子を使用しません。直接ヒープセグメントに割り当てられます。

---

### アロケータ設計の目的

* **適切な GC トリガー**: 割り当て予算（アロケータが超えると GC を起動するしきい値）やセグメント状況に基づき GC を起動
* **オブジェクト局所性の保持**: 同じヒープセグメントにまとめて割り当てられたオブジェクトを近接アドレスに配置
* **キャッシュ効率**: アロケーション量子単位で確保し、確保時にゼロ初期化して CPU キャッシュをウォームアップ
* **効率的なロック**: 割り当てコンテキストはスレッド専有のため、オブジェクト割り当て時にロック不要（量子が尽きるまで）
* **メモリ整合性**: 新規オブジェクトは必ずゼロ初期化
* **ヒープの走査可能性維持**: 残りメモリが次オブジェクトに足りない場合は空きオブジェクトとして登録し、新しい量子を確保

---

### 割り当て API

```cpp
Object* GCHeap::Alloc(size_t size, DWORD flags);
Object* GCHeap::Alloc(alloc_context* acontext, size_t size, DWORD flags);
```

小オブジェクト・大オブジェクト両方に利用可能。

大オブジェクトヒープ (LOH) に直接割り当てる関数もあります。

```cpp
Object* GCHeap::AllocLHeap(size_t size, DWORD flags);
```

## コレクタの設計

### GC の目標

GC の目的は「極めて効率的にメモリを管理し、マネージコードを書く開発者の負担を最小化する」ことです。効率とは以下を意味します。

* ゴミ（不要だが割り当てられているオブジェクト）を放置しない頻度で GC を行う
* CPU 時間を無駄にしないため、GC 頻度は可能な限り低くする
* GC は生産的であるべき（少量しか回収できない GC は無駄）
* 高速であること（低レイテンシ要件のワークロード多数）
* 開発者は GC の詳細を知らなくても適正なメモリ利用を実現できる
* ワークロードに応じて自己調整できる

---

### 論理的なマネージヒープの構造

CLR GC は**世代別 GC**です。世代 *N* を回収すると、生き残ったオブジェクトは世代 *N+1* へ昇格（promotion）します。例外的に降格や非昇格もあります。

* **小オブジェクトヒープ (SOH)**: gen0, gen1, gen2 の 3 世代
  gen0/gen1 は短命オブジェクト用の「エフェメラル世代」。
* **大オブジェクトヒープ (LOH)**: gen3 の 1 世代のみ（常に gen2 回収時に処理）

割り当ては常に最年少世代（小オブジェクトは gen0、大オブジェクトは gen3）で行います。

---

### 物理的なマネージヒープの構造

* **ヒープセグメント**: GC が OS から取得する連続メモリブロック
* セグメントの種類: 小オブジェクト用、大オブジェクト用、ピン留めオブジェクト用
* 各ヒープは少なくとも 1 つの小オブジェクトセグメントと 1 つの大オブジェクトセグメントを持つ
* 読み取り専用 (RO) セグメントは NonGC ヒープに置かれる
* 小オブジェクトヒープには常に 1 つのエフェメラルセグメント（gen0/gen1）が存在
* 大オブジェクトヒープには 1 個以上のセグメントが存在
* メモリは低アドレスから高アドレスへ消費される
* 空のセグメントは削除または再利用可能（再利用は小オブジェクトヒープのみ）

### 割り当て予算 (Allocation Budget)

割り当て予算は、各世代に論理的に関連付けられた概念です。
これは、その世代に対する GC をトリガーするサイズ上限です。

予算は主にその世代の**生存率**（GC 後に残るオブジェクトの割合）に基づいて設定されます。生存率が高ければ予算は大きくなり、次回の GC では不要オブジェクトと生存オブジェクトの比率がより改善されることを期待します。

---

### 収集する世代の決定

GC をトリガーした場合、まずどの世代を回収するかを決定します。割り当て予算以外にも、以下の要素が考慮されます。

* **世代の断片化 (fragmentation)**
  断片化が高い場合、その世代の回収は生産的である可能性が高い。
* **マシンのメモリ負荷**
  メモリ負荷が高すぎる場合、より積極的に GC を行い空き領域を増やす（ページングを防ぐため）。
* **エフェメラルセグメントの空き状況**
  空きが少ない場合、新規セグメント取得を避けるため、より頻繁に gen1 収集（エフェメラル収集）を行うことがある。

---

### GC の流れ

#### マークフェーズ (Mark Phase)

目的は**すべての生存オブジェクトを特定する**ことです。

世代別 GC の利点は、ヒープ全体を調べる必要がなく、必要な部分だけを収集できることです。エフェメラル世代を収集するとき、GC は EE から報告される生存オブジェクト情報を利用します。加えて、古い世代のオブジェクトが若い世代のオブジェクトを参照している場合、それらも生存と見なされます。

古い世代のマーキングには**カード (cards)** を使用します。カードは JIT ヘルパーによって代入操作時に設定され、エフェメラル範囲への参照が見つかると、その元の位置を表すカードバイトが設定されます。エフェメラル収集時、GC はこのカード集合を参照し、該当するオブジェクトだけを調べます。

---

#### プランフェーズ (Plan Phase)

このフェーズでは、コンパクションをシミュレーションし、その効果を見積もります。コンパクションが有効と判断されれば実行し、そうでなければスイープを行います。

---

#### リロケートフェーズ (Relocate Phase)

コンパクションを行う場合、オブジェクトを移動させるため、それらを参照しているポインタを更新する必要があります。リロケートフェーズでは、収集対象世代内のオブジェクトを指すすべての参照を探して更新します。マークフェーズは生存オブジェクトのみを調べるため、弱参照 (weak references) は考慮しません。

---

#### コンパクトフェーズ (Compact Phase)

プランフェーズで移動先アドレスは既に計算済みのため、このフェーズは単純にオブジェクトを新しい場所へコピーします。

---

#### スイープフェーズ (Sweep Phase)

生存オブジェクトの間にある死んだ領域を探し、そこを空きオブジェクトとして作成します。隣接する死んだオブジェクトは一つの空きオブジェクトにまとめます。すべての空きオブジェクトは**フリーリスト (freelist)** に登録されます。

---

## コードフロー

**用語**:

* **WKS GC**: ワークステーション GC
* **SVR GC**: サーバー GC

---

### 機能的挙動

#### WKS GC（同時 GC 無効）

1. ユーザースレッドが割り当て予算を使い果たし GC をトリガー。
2. GC が `SuspendEE` を呼び出し、マネージスレッドを停止。
3. GC が「破棄する世代 (generation to condemn)」を決定。
4. マークフェーズ実行。
5. プランフェーズ実行し、コンパクションを行うか判定。
6. 行う場合はリロケート＋コンパクトフェーズ、行わない場合はスイープフェーズ。
7. `RestartEE` を呼び、マネージスレッドを再開。
8. ユーザースレッド実行再開。

---

#### WKS GC（同時 GC 有効）

バックグラウンド GC の流れ:

1. ユーザースレッドが割り当て予算を使い果たし GC をトリガー。
2. `SuspendEE` を呼び出しマネージスレッドを停止。
3. バックグラウンド GC 実行可否を判定。
4. 実行する場合、バックグラウンド GC スレッドを起床し、`RestartEE` でマネージスレッドを再開。
5. バックグラウンド GC 実行中もマネージスレッドは割り当てを継続。
6. ユーザースレッドが再度予算を使い果たすと、エフェメラル GC（フォアグラウンド GC）を実行（これは「WKS GC（同時 GC 無効）」と同じ手順）。
7. バックグラウンド GC が再び `SuspendEE` を呼び、マーキングを完了し、`RestartEE` で同時スイープを開始。
8. バックグラウンド GC 完了。

---

#### SVR GC（同時 GC 無効）

1. ユーザースレッドが予算を使い果たし GC をトリガー。
2. サーバー GC スレッドが起床し、`SuspendEE` でマネージスレッドを停止。
3. サーバー GC スレッドが WKS GC と同様のフェーズを実行。
4. `RestartEE` でマネージスレッド再開。
5. ユーザースレッド実行再開。

---

#### SVR GC（同時 GC 有効）

基本的に「WKS GC（同時 GC 有効）」と同じですが、非バックグラウンド GC 部分はサーバー GC スレッドで実行されます。

---

## 物理アーキテクチャ

この節はコードフロー理解の補助のためです。

ユーザースレッドが割り当てコンテキストの空き不足により `try_allocate_more_space` を呼び、新しいコンテキストを取得します。

`try_allocate_more_space` が GC を必要とする場合、`GarbageCollectGeneration` を呼び出します。

---

### WKS GC（同時 GC 無効）のコードフロー

```cpp
GarbageCollectGeneration()
{
    SuspendEE();
    garbage_collect();
    RestartEE();
}

garbage_collect()
{
    generation_to_condemn();
    gc1();
}

gc1()
{
    mark_phase();
    plan_phase();
}

plan_phase()
{
    // 実際にコンパクトするかどうかを決定
    if (compact)
    {
        relocate_phase();
        compact_phase();
    }
    else
        make_free_lists();
}
```

---

### WKS GC（同時 GC 有効）のバックグラウンド GC フロー

```cpp
GarbageCollectGeneration()
{
    SuspendEE();
    garbage_collect();
    RestartEE();
}

garbage_collect()
{
    generation_to_condemn();
    // バックグラウンド GC 実行を決定
    do_background_gc();
}

do_background_gc()
{
    init_background_gc();
    start_c_gc();

    // BGC により再開されるまで待機
    wait_to_proceed();
}

bgc_thread_function()
{
    while (1)
    {
        // イベント待機
        // 起床
        gc1();
    }
}

gc1()
{
    background_mark_phase();
    background_sweep();
}
```
